# Laya 长上下文方向

2026-09-21 用户已确定：本轮按 8,192 token 上下文上限准备数据和训练，预算包含正文、问题、候选项及特殊 token。保留长短样本混合，短文本无需重复填满。8k 计算容量与测速已通过；正式数据尚未准备完成，业务效果尚未验证。16k、32k 保留为后续研究，不属于本轮训练目标。

## 上下文边界

- Jev 1.13 的整个请求上限为 64k token，同时 `state` 加最长单个问题不得超过 32k token；不能将 64k 当作单段材料预算。[TypeSafe 官方模型说明](https://docs.typesafe.ai/models)，2026-09-21 核对。
- Laya 当前缓存检查点的 `max_len` 为 512；底座 ModernBERT-large 的原生上下文为 8,192 token。[底座模型卡](https://huggingface.co/answerdotai/ModernBERT-large)
- 底座支持的长度、一次训练能运行的长度、经过业务验证的有效长度是三个不同指标。前两者已确认到 8k，尚未验证第三个。
- 这一阶段不将配置直接改为 32k。超过原生 8k，需要另行选择支持更长上下文的底座，或设计上下文扩展训练及评估。

## Kev 的上下文与 16k / 32k 方向

2026-09-21 核对 Kev 源码提交 `4f8110a3f8620cc3a182ae9a708e4398492c4b1a`：

- 训练编码默认 `MAX_STATE=384`、`MAX_BRANCH=1024`；后者包括正文、单个问题、候选项和特殊 token。训练筛选还要求整个打包记录不超过 2,048 token，这不是单个问题的窗口。
- 服务端 `INFER_MAX_STATE=8192`、`INFER_MAX_BRANCH=8192`，因此正文和一道问题合计上限是 8,192 token。README 明确说明训练未覆盖更长上下文。[README](https://github.com/jaredpalmer/kev/blob/4f8110a3f8620cc3a182ae9a708e4398492c4b1a/README.md#limitations)、[编码逻辑](https://github.com/jaredpalmer/kev/blob/4f8110a3f8620cc3a182ae9a708e4398492c4b1a/kev/model.py)、[服务逻辑](https://github.com/jaredpalmer/kev/blob/4f8110a3f8620cc3a182ae9a708e4398492c4b1a/kev/serve.py)。
- 原型 Kev-0.5B 使用的 Qwen2.5-0.5B 配置窗口为 32,768；当前 Kev-0.8B 使用的 Qwen3.5-0.8B-Base 配置窗口为 262,144。这些是底座配置，不是 Kev 已训练或已验证的业务长度。[Qwen2.5 配置](https://huggingface.co/Qwen/Qwen2.5-0.5B/blob/main/config.json)、[Qwen3.5 配置](https://huggingface.co/Qwen/Qwen3.5-0.8B-Base/blob/main/config.json)。

继续扩大时保留两条候选路径：对 Laya 的 ModernBERT 做专门的上下文扩展；或参考 Kev 的决策头方法，采用原生支持长上下文的底座重新训练。更换底座不能直接沿用 Laya 编码器权重。两条路径均须先做 16k 容量测试，再评估 32k，并在相同业务材料上比较准确率、校准和成本。当前尚未执行 16k / 32k 测试，显存余量不代表长文本效果已获验证。

## 训练与数据设计

1. 保留原始完整业务材料和标签，按实际分词长度分桶：不超过 512、512–2k、2k–4k、4k–8k。长度按“问题、规则、候选项、正文和特殊 token”合计，不能只计算正文。
2. 训练样本覆盖多轮客服记录、订单状态与规则组合、长页面或 AX 状态、检索相关性。长文本必须包含真实决策信息，测速时使用的重复文本不能转成训练集。
3. 混合长短样本，预处理和训练统一采用 8k 上限；具体比例由真实数据长度分布确定。4k 作为评测对照，不再作为本轮正式训练的固定上限。
4. 单独配置问题与正文的预算。原实现有 `head_max_len=192` 和每个候选项最多 48 token 的裁剪逻辑；扩大正文预算时，也要检查规则与候选项是否被过度截断。
5. 按订单、客户、会话或来源文档分组切分训练、模型选择、校准与最终测试。原样本和对照衍生样本必须留在同一划分。
6. 以 LoRA 加决策头为第一条训练路径，使用实际验证通过的 BF16 与梯度检查点配置；根据显存决定微批量，以梯度累积调整有效批量。

## 评测必须回答的问题

- 相同原始材料下，512 截断、2k、4k、8k 的准确率、Macro-F1、Brier/NLL/ECE 是否改善？按长度桶和业务类别分别报告。
- 将决定标签的证据放在开头、中部或结尾，模型能否保持判断？删除该证据后，预测是否相应变化？
- 加入无关对话、历史订单、相似规则和矛盾状态后，是否仍能找到当前有效信息？
- 同一短样本放入长上下文后，是否出现准确率回退或过度自信？
- 不同候选项数量、规则长度、中文比例和多问题请求，是否改变容量与效果？
- 同时记录训练吞吐、推理延迟、显存峰值、截断率，以及原始材料中关键证据被保留的比例。

只有长文本数据和隔离测试显示改善，才把较长预算作为业务默认值。训练能够执行或合成测速损失下降，都不等于业务效果提升。

## 已完成与待完成

本机已跑通 1k、2k 和 4k 的 LoRA 训练测速；2k、4k 使用编码器梯度检查点。2k 未开启重算时触及人为设置的 16 GiB MPS 进程预算，这不是机器全部内存的上限。

RTX 5090 已完成 2k、4k、8k 测速，并验证 8k BF16 LoRA 的 batch 1、2、4，以及 8k 全量分类微调。
8k、batch 4、BF16 LoRA 加编码器和决策头重算可作为下一阶段起始配置：约 3.114 秒/步、1.285 条/秒，分配显存峰值 10.21 GiB。
远程使用隔离目录和虚拟环境，复用已有 CUDA PyTorch，权重在服务器直接下载并核对 SHA256。
详细结果见 [5090 测速报告](../results/cuda-5090-training-speed-2026-09-21.md)。正式训练集和测试集仍待准备，尚未验证长文本业务效果。
