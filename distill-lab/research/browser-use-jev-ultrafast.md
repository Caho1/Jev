## 应借鉴的结构

```text
目标 + 当前可见 DOM 控件/状态 + 已执行历史
    → operation + click_target + type_text_target + select_target
    → 仅消费被选中 operation 对应的目标
    → 验证页面与目标仍有效 → 执行 → 重新观察 → 独立验证结果
```

这适合训练 Laya 承担浏览器的动作与目标决策。文本填写由单独的生成模型处理，
执行器负责 DOM 引用、可见性、遮挡、页面变化和动作执行。
这些职责无需都塞进分类模型。

- [snapshot.js](https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/jev_ultrafast/snapshot.js)
  直接读取 DOM 和 ARIA 属性，提取可见可用的控件及其名称、当前值和选中/展开状态。
  决策不依赖 OCR；截图用于可选的检查界面与录制。
- [model.py](https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/jev_ultrafast/model.py)
  构造多个 Choice 题目，一次 HTTP 请求同时询问操作与各类目标。
  这些是 API 中的题目分组，不代表要在 Laya 内创建四套独立神经网络头。
- [agent.py](https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/jev_ultrafast/agent.py)
  仅在 `TYPE_TEXT` 时调用文字模型。`SELECT` 的目标同时指定控件和选项，不能仅预测下拉框。
  `DONE` 是模型选择，仍需要独立的结果检查。

其八类操作为 CLICK、TYPE_TEXT、SELECT、SCROLL_UP、SCROLL_DOWN、WAIT、DONE、BLOCKED；
每步按实际可执行项动态生成。当前快照最多保留 250 条元素动作，再追加滚动/等待项；
250 条动作不等于 250 个控件，一个输入框可以同时贡献 click 和 fill。
可见正文另有 6,000 字符限制，这不是 6,000 tokens，也不保证能装进 Laya 的 8K 预算。

## 与我们现有模型的差距

| 项目 | 当前已完成的工作 | 下一轮需要对齐 |
|---|---|---|
| 观察来源 | Mind2Web 静态 HTML 候选；没有使用 OCR | 运行时可见 DOM、字段状态、前后变化 |
| 训练目标 | 单控件是/否，2,068 对 | 操作 Choice + 对应目标的同页候选选择 |
| 最近回放 | operation + 一个通用 item | 按操作划分兼容目标，SELECT 包含选项 |
| 行为覆盖 | CLICK / TYPE / SELECT | 补充等待、滚动、完成、阻塞与恢复 |
| 输入参数 | 当前 grounding 文件未保留完整填充值/选项监督 | 从训练源恢复有标注的参数；文本生成单独评测 |
| 评价 | 离线选点/排序，人工历史 | 先离线步骤正确率，再测实际任务完成率 |

现有 519 个训练步骤、78 个开发步骤仍然有用；不要把静态 HTML 的候选当作已验证的当前视口控件。
候选池生成代码并没有运行布局引擎，不能凭空补上 visibility、坐标或执行结果。

当前 BM25 前 64 个候选只在 40/78 个开发步骤中保留正确目标。这个召回瓶颈需要先解决。
按控件可执行操作分组、保留正确语义字段和提高候选覆盖是改进方向，实际收益仍需开发集验证。
不得在开发或测试时根据答案强行补入正确目标。

上一轮独立二分类训练在完整开发集上的 Recall@24 从 16.67% 降到 11.54%。
因此下一轮应把原始 Laya 与该检查点作为对照，不能默认沿用旧检查点更好。
数据、训练设置与来源见[上一轮训练记录](../results/computer-use-grounding-cuda-v1/README.md)。

## 接口审查结果

离线提取上游 `action_space/choose/validate_choice` 代码，用合成页面和模拟响应验证了请求构造，
没有 HTTP、浏览器或优化器调用。结果见 [protocol-audit.json](jev-ultrafast-protocol-audit.json)。

现有回放器不能直接接收其原始请求，原因包括：

1. 上游 instructions 和候选描述允许 JSON 对象；当前 v1 只允许字符串。
2. 目标题可能只有一个候选；当前 v1 和本地 Choice 编码要求至少两个。
3. 目标监督与当前操作有关，不能要求所有目标题同时匹配同一个人工点击答案。

适配时需明确 JSON 的统一序列化、单候选的确定性处理，以及只训练人工操作对应的目标题。
例如人工操作是 CLICK，就不把被点击按钮也标成 TYPE_TEXT 的目标。
Jev 给出的其他假设操作目标可保留用于分析，但不能直接冒充人工标签。
旧回放里的教师概率属于另一种请求格式，不能套用到新的候选集合。

## 后续数据与训练顺序

1. **冻结浏览器协议。** 对同一可观察状态构造相同候选和题目，让 Jev、原始 Laya、微调版接收相同输入。
   先保持 8K 上限，统计整个请求的编码长度和候选覆盖；超限分组或重新设计表示，不能静默截断目标。
2. **准备同页候选监督。** 复用已有 Mind2Web 训练划分，随机化选项位置，保留人工多正例，
   用候选间的选择损失替代只对单控件打是/否。仅训练集允许有监督采样与难负例挖掘。
3. **采集浏览器状态转换。** 补充搜索/自动补全、表单、下拉、筛选/排序、分页、弹窗关闭，
   以及加载中、无结果、重复动作、真实完成等状态。中文部分来自原生中文网页与中文任务，沿用不翻译要求。
   同一任务模板、同一流程的相邻步骤整体分组，不随机拆到训练和测试两边。
4. **采集并核验教师输出。** 固定 Jev 版本，保存完整请求与概率；结合人工标注和实际执行结果筛选。
   Jev 的 DONE 或自报成功本身不构成真值。开发输出不写回训练集。
5. **先做本地小规模验证。** 比较候选召回、operation 正确率、操作与目标联合正确率；
   流程对齐后再做浏览器闭环，比较独立验证的任务成功率、误报完成、p50/p95 延迟与调用量。

等待/阻塞等缺失标签必须来自可观察状态及人工或可验证的任务结果；
不能将某条 Mind2Web 轨迹的最后一步直接改标 DONE，也不能将候选检索失败直接标成真实 BLOCKED。
原校准和内部留出页面继续封存；开发用于选择方案，最终留出只在方案冻结后使用。

## 速度与覆盖边界

上游的速度收益包含快照读取、减少浏览器协议往返、目标有效性检查和等待策略；换一个模型不等于自动继承这些收益。
多题一次 HTTP 调用也不等于我们本地 Laya 已实现共享状态的一次前向。
当前本地回放仍逐题运行，需要单独测批处理/共享编码是否值得实现。

[上游性能记录](https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/docs/performance.md)
中的 7 秒左右结果是单一 Flights 任务的小规模重复实验，不能当成通用生产成功率。
当前 MVP 不覆盖 shadow roots、iframe、canvas、新标签页和嵌套滚动等场景。
第一阶段优先普通 DOM 网页的搜索、表单和筛选任务，按真实终态验证是否完成。

本次完成的是源码审查、离线接口探针和方案调整；尚未完成 ultrafast 适配器、浏览器轨迹采集或下一轮微调。
