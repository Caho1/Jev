## 结论

新增了 Jev + Codex 官方 Computer Use 工具的实验性适配器，真实网页可用性优于原 Swift 路径在本轮遇到的表现：旧路径读取 GitHub/Bing 会截断，而新路径能完成 Wikipedia 设置及 PyPI 五步导航。但**没有证据证明整体优于 Codex 原版**。唯一同任务计时对照中，Jev 三步设置 8.238 秒，官方工具直接执行 6.180 秒，前者更慢。

该对照是预先规划好动作的工具执行计时，双方都排除主模型规划和人工准备时间，不是两套完整自治 Agent 的公平盲测。不能据此声称完整 Codex 更快或 Jev 更快。当前主要价值是减少简单决策往返主模型，并改善可用范围；还需要独立、多任务、多轮的端到端对照。

## 官方 Browser 的实际状态

尝试了 Codex 内置浏览器：创建/导航到 Wikipedia 与 GitHub，以及重新绑定标签页，均多次超时。后续标签页列表显示 GitHub 已加载，但取回操作句柄依然超时，因此 **内置 Browser Tab 路径没有通过实测**。

本轮成功执行使用的是 Codex 官方 CUA 的 `cua.getApp('com.google.Chrome')`，属于官方 Computer Use 控制原生 Chrome，不等同于内置 Browser。适配器可接收文档中的 App/Tab 接口，但接口兼容代码不能算作实际 Tab 集成成功。

Bing 测试后官方原生控件读取也出现异常；关闭仅本轮创建的 Bing 标签页后，PyPI 状态仍为空。此时停止 UI 测试，保留连接故障记录，没有用未经公开的调试接口绕过。

## 迭代内容

- `scripts/official_browser.mjs`：Jev 决策与官方执行工具分离，使用官方公开的观察、点击、输入和按键接口。
- 只发送当前任务相关候选和必要状态，避免把长文章、浏览器其他标签页和无关控件发送给模型。完整页面留在本地用于核验。
- 网络决策后重新观察，重新解析控件编号；目标或页面范围变化时停止。
- 保留概率门槛、最终可见证据校验，模型 DONE 不能替代成功断言。
- 增加显式前置条件、后置条件、单一可执行规则的直通路径。默认不会因为只剩一个候选就跳过模型；必须由宿主明确声明 deterministic 且提供前置条件。
- 处理导航期间暂时无网页节点的现象，区分观察失败与操作失败，不自动重复已提交的动作。
- 限流/验证页的部分标题识别、重复动作保护、步骤和时间预算、失败计时记录。
- 更新 Skill 路由及浏览器说明；仍标为实验性，未把本轮样本外推成通用能力。
